## 2026-07-25: Bound the RefPack decoder, refuse BTREE/HUFF

`CompressionManager::decompressData` takes a `destLen` and threw it away for all
three EAC codecs. `REF_decode` writes through a bare `*d++` until it meets an eof
opcode; the stream's declared `ulen` is parsed and never used. A `.map` that
declares 4096 bytes and expands to 8960 writes 4864 bytes past its allocation.

This is reachable from data the player did not author, twice over:

- `DataChunk.cpp:98` — map *enumeration* decompresses every `.map` on disk at
  startup to read its metadata, including maps a peer transferred in a lobby that
  the player never opened.
- `ConnectionManager.cpp:843` — inbound peer packets, no file needed.

Added `REF_decode_bounded` beside the original (left untouched, so the dev tools
and any other caller keep working). It gates every read and write against both
extents, rejects a declared `ulen` larger than the destination up front, and
rejects a back-reference that underflows the start of the buffer —
`ref = d-1-offset` with a 17-bit offset could point before `dest` and splice
out-of-bounds heap into the output.

BTREE and HUFF are refused rather than fixed. Both are equally unbounded, and
`BTREE_chase` recurses over a left/right table indexed by stream-supplied bytes,
so a cyclic tree exhausts the stack. Bounding only RefPack would have been
theatre: the four-byte magic alone picks the codec, so a crafted file changes
`EAR\0` to `EAB\0` and walks around the new check. Refusing costs nothing —
a scan of the 37 BIG archives in a full install found 171 maps: 166 `EAR\0`,
4 uncompressed, 1 `ZL5\0`, and no `EAB`/`EAH` anywhere. `getPreferredCompression()`
is REFPACK unconditionally and nothing in the tree ever asks for the other two.

Validation (details and reproduction in
[`../architecture/COMPRESSION.md`](../architecture/COMPRESSION.md) §5):

- 64 round-trip trials, 4 content shapes × 16 sizes (1 B – 70 KB): the bounded
  decoder is byte-for-byte identical to the original, same return value, same
  bytes consumed. Safety did not cost correctness.
- 150 000 mutated streams decoded with source and destination flush against
  `PROT_NONE` guard pages: 35 901 accepted, 114 099 refused, zero faults. The
  24% acceptance rate is the part that matters — it proves the deep opcode paths
  ran instead of everything dying at the header.
- Differential: one hand-built over-expanding stream, same buffer — bounded
  returns 0, legacy takes SIGBUS.

Two things cost real time and are written up as gotchas:

**`REF_encode` and `REF_decode` disagree on header byte order.** The encoder
emits the magic little-endian (`FB 10`), the decoder reads big-endian and sees
`0xFB10`, takes the `&0x8000` four-byte-size branch, and runs off the end of a
buffer it just produced. Shipped data is `10 FB` and is fine. Building a test
corpus with the in-tree encoder and feeding it to the in-tree decoder therefore
hangs, and it looks exactly like a bug in whatever you just wrote. `REF_size` and
`REF_is` accept both orders, which hides it further. Upstream behaviour, not
changed here — the test harness swaps bytes 0 and 1 after encoding.

**AddressSanitizer is unusable on this machine.** A static `hello world` built
with `-fsanitize=address` never reaches `main` (macOS 25.5). Guard pages replaced
it and are strictly stronger for linear overruns, which is what was being tested.

## 2026-07-25: Audit fix pass — 22 findings, one reverted

A per-file agent pass applied 28 verified audit findings across 26 files, each
reviewed independently afterwards. 22 applied, 2 declined as not-real, 19 files
came through clean.

Themes: bounding untrusted file and wire input on paths the iPad build walks at
startup (map cache, prefs, INI module names, LAN datagrams, shore-line scans),
a cluster of one-token logic inversions (`vector3.h` `Quick_Length` sort swap,
inverted `strcmp`, inverted low-detail toggle, missing `abs()`), the supply-truck
save/load stall, and deletion of ~79 lines of unguarded per-frame stderr
instrumentation from the client path — including an unbounded `sprintf` of a
data-driven font name into a 256-byte stack buffer.

### The one that had to be reverted

`DockUpdate.cpp` finding 3.5 targeted a real defect — `m_numberApproachPositionBones`
is never serialised, so after a load it sits at its constructor value of −1 forever,
because `m_positionsLoaded` *is* serialised and short-circuits all six lazy
`if( m_positionsLoaded == FALSE ) loadDockPositions();` call sites. The counter
staying −1 permanently disables the `== 0` boneless approach-point bias, and
workers clump at the building centre instead of queueing.

The applied remedy was `m_positionsLoaded = FALSE;` in `loadPostProcess()`, on the
stated rationale that re-running `loadDockPositions()` "reproduces the same values
that were xfered". That rationale is false, and the review caught it.
`loadDockPositions()` sources bones from `Drawable::getPristineBonePositions`,
which resolves against the drawable's **current** `m_conditionState`
(`Drawable.cpp:805`). `m_positionsLoaded` is a one-shot latch, so the xfered
coordinates are "bones as of first use" while a re-run yields "bones as of the
first post-load consumer" — a different condition state if the building is
damaged, fortified/upgraded, or mid-dock (this module sets `MODELCONDITION_DOCKING*`
on its own object).

The concrete harm is worse than the bug. The non-dynamic branch does
`Coord3D approachBones[DEFAULT_APPROACH_VECTOR_SIZE] = {0};` and then copies
indices `[0, m_numberApproachPositions)` into `m_approachPositions`
unconditionally. A condition-state model exposing fewer `DockWaiting` bones than
the pre-save one overwrites good restored coordinates with (0,0,0) — producing
exactly the clumping the fix claimed to prevent. It also re-derives the counter
rather than restoring it, so it can come back 0 where it was 4, switching *on* a
branch that was off pre-save.

Replaced with a counter-only recompute: repair `m_numberApproachPositionBones`
alone, leave the latch `TRUE` and all four restored position members untouched.
The reviewer's alternative was a version-bumped `xferInt` of the counter, which is
cleaner in isolation but changes the save byte stream and the CRC; the counter-only
recompute repairs existing saves at zero format cost. The no-drawable case is left
alone deliberately — `loadDockPositions` only ever writes the counter inside
`if (myDrawable)`, so clearing the latch there would make all six call sites
re-enter it every frame for the rest of the match.

The other `DockUpdate` hunk (3.1) is correct and shipped: `m_approachPositionReached[vectorIndex] = unpack;`
was missing from `xfer()`, so the load direction never wrote back. `BoolVector` is
`std::vector<bool>`, so the temporary is genuinely required and the store is a
verified no-op on both save and CRC directions. That is the supply-truck-stalls-
after-every-load bug.

### Gated

`SpawnBehavior::reclaimOrphanSpawn` had `prevName.compare(*tempName) != 0` where
`compare` is `strcmp` semantics — it skipped every entry that *differed* from the
previous one, and since `prevName` starts empty and is only assigned past the
`continue`, nothing ever got through. The function returned `nullptr` on every
call in every build, making `CanReclaimOrphans` dead everywhere.

Repairing it changes the simulation: reclaiming an orphan skips an object
creation, so the logic frame and CRC diverge from retail replays and from peers
without the fix. Gated behind `RETAIL_COMPATIBLE_CRC` (defaults to 1) to match the
convention already used elsewhere in the tree, so the default build keeps retail
behaviour. Build with `-DRETAIL_COMPATIBLE_CRC=0` to take it.

`FXListDie` (3.4) is in the same category and is inert in the default config for
the same reason — `RETAIL_COMPATIBLE_XFER_SAVE` keeps `currentVersion` at 1, so
`upgradeMuxXfer` is never written. The gating is correct (appending bytes under
version 1 would over-run the module's block in a retail save) but the practical
effect is that the `StartsActive = No` + `TriggeredBy` death-FX loss still happens
by default.
