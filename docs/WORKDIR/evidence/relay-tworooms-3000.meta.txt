SETUP
  Both hosts on the VPS, one per network namespace (gx 10.200.0.2, gx2 10.200.1.2), because
  relay mode forces a wildcard bind and multi-instance disables relay mode on Linux.
  Options.ini on both machines reduced to `RelayAddress` alone - no RelayRoom, no
  LocalVirtualIP. Every room token and every virtual address below was therefore generated
  or assigned, not configured by hand.

  hostA   netns gx    room g3athw1ptgr2u9   maps\twilight flame\twilight flame.map
  hostB   netns gx2   room g35spj53fe4ow9   maps\alpine assault\alpine assault.map

  Two hosts generated two different room tokens with no coordination. Each was assigned
  10.42.0.1 IN ITS OWN ROOM - the same address in two rooms at once, which is what makes
  rooms separate address spaces rather than a naming convention.

BROWSE (docs/WORKDIR/evidence/relay-tworooms-browse.txt)
  Two consecutive browses from macOS both returned 2 games, in 2 rooms, both host=10.42.0.1,
  distinguished by room and map. Each browsing process generated its own throwaway room.
  After hostA exited, a third browse returned 1 game - hostA dropped off the list purely by
  going quiet, with no teardown message, which is the failure mode that has to work.

AMBIGUOUS JOIN (docs/WORKDIR/evidence/relay-tworooms-ambiguous-join-refusal.txt)
  `-lanjoin 10.42.0.1` with no room pin exits 1 and names both candidate rooms. This is
  correct and is itself evidence: addresses are allocated per room, so a host address alone
  cannot identify a game once more than one room exists. chooseRelayRoom says so; this
  confirms it against a live relay rather than a comment.

JOINS - both rooms, independently
  roomA  macOS joined with GENERALSX_LANROOM pinned; relay assigned it 10.42.0.2, correctly
         excluding the 10.42.0.1 already held by the host.
  roomB  macOS joined with NO pin - it browsed, matched the listing, took the room off the
         LISTING and entered it. That is the full "a browser pick moves you into one" path,
         which had zero call sites before 43bcadd8b.

HARNESS BUG FOUND AND FIXED (mine, not the game's)
  The first attempt started both hosts as background jobs of an ssh session with no nohup,
  so they took SIGHUP when it closed. A browse during the window then showed 1 of 2 games
  and looked like a game-list bug. It was not: ADVERT_TIMEOUT_MS is 15s, the browse landed
  15-20s after both hosts died, and the staleness cutoff fell between their last two
  advertisements. Re-run with `setsid nohup ... < /dev/null`, both browses returned 2 of 2.
  Rule: a host started over ssh must be detached, or it dies with the session and the
  symptom presents as a matchmaking fault.
