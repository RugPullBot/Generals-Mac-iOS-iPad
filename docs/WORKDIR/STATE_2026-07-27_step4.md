## Blocker 5 is now THE task. What we know and what limits us

The divergence happened at or before frame 100. We cannot currently say *where*, and that is the
next thing to fix:

* **The CRC interval cannot go below 100 in a shipping build.** `NET_CRC_INTERVAL` is 1 under
  DEBUG_CRC and 100 otherwise (`Core/.../Network.cpp:57-60`); `GameInfo::setCRCInterval` clamps to
  <=100 (`GameInfo.h:219`); and `-NetCRCInterval`'s parse body *and* its table entry are both inside
  `#ifdef DEBUG_CRC` (`CommandLine.cpp:322-331`, `:1231/:1275/:1279`). So frame 105 is simply the
  first time anyone looked.
* **Do NOT just build one side with DEBUG_CRC to get finer resolution.** The `TheModuleFactory`
  block at `GameLogic.cpp:4293-4305` is inside `#ifdef DEBUG_CRC`, so a DEBUG_CRC build hashes
  different bytes and would mismatch a release peer *by construction*. Any added resolution has to
  come from a release-safe change (lower the clamp, or an fprintf-only per-frame CRC that does not
  touch the xfer stream).
* The scope doc's plan still stands and is now clearly the next move: **de-fold `SimulationMathCrc`**
  (make its inputs `volatile`; 10 of its 17 libm call sites are constant-folded at -O2, so today it
  measures the compiler rather than libm) and compare the value across peers. That isolates
  "libm disagrees" from "the simulation diverged for some other reason" before anyone starts
  bisecting frames.

## Traps found tonight, all of which failed silently

* **Never capture the game's stderr through a pipe.** ProcessStartInfo + RedirectStandardError + a
  `Task.Run` drain hangs the game outright: a PowerShell scriptblock cast to `[Action]` runs on a
  thread-pool thread with no runspace, the body never executes, nothing reads the pipe, and the child
  blocks on its next stderr write. `longrun.ps1` had this bug too and its stderr file was never
  created on any run. Redirect to a file with the shell.
* **The game window does not land in the same place twice** — three launches, three positions. Use
  client-relative coordinates translated through `ClientToScreen`.
* **A move and a click in one `SendInput` batch clicks the wrong control.** The shell resolves the
  hovered control once per frame, so pressing in the same batch as the move hits the *previously*
  hovered control. Clicking NETWORK's coordinate this way opened ONLINE. Move, dwell ~900 ms, then
  press separately.
* **`SendInput` silently returns 0** if the INPUT struct size is wrong. Do not hand-pad it.
* **DXVK floods stderr on Windows** — 17,253 lines in one run that never left the main menu, one
  synchronous render-thread write per frame. `DXVK_LOG_LEVEL=none`, as macOS `run.sh` already does.
