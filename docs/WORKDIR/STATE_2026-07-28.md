# Project state — 2026-07-28 (overnight session)

## Headline

**The cross-platform desync root cause was found, proven at bit level, and fixed.** Blocker 5 went
from "unmeasured, possibly a multi-week deterministic-math project" to a one-line cause with a
working fix, in one session. **The three-way LAN lobby also works**, which was blocker 6.

## Root cause

Apple's libm (arm64) and MSVC's UCRT (x64) return results **one ULP apart** for `cosf`/`sinf` at
angles near 45 degrees. Captured from two peers in a live match at the same clean commit, dumping
every object's raw transform bits at frame 0:

```
mac BF34D116  win BF34D117    -0.706315398 vs -0.706315458   45.06 deg
mac BF34919D  win BF34919E    -0.705346882 vs -0.705346942   45.14 deg
mac BF349F7C  win BF349F7D    -0.705558538 vs -0.705558598   45.13 deg
mac 3F34D111  win 3F34D112     0.706315100 vs  0.706315160   45.06 deg
```

Six objects of 323, delta 5.96e-08 = 2^-24 every time. `Thing::setOrientation` (Thing.cpp:232-241)
writes those raw results into the object transform; `Object::crc` (Object.cpp:4007) hashes the 48
bytes with **no epsilon**. One bit ends the match before frame 1. Rocks survived only because they
sit at angles where the two libraries happen to agree.

## The fix

`Core/Libraries/Source/WWVegas/WWMath/gamemath.h` implements Sin, Cos, Tan, ASin, ACos, Atan and
Atan2 using **only IEEE-754 basic arithmetic** — which the standard requires to be correctly rounded,
so every conforming platform produces identical bits. Transcendentals carry no such requirement,
which is exactly why libm implementations differ.

Cody-Waite range reduction plus Taylor series in double, Horner form so the *order* of roundings is
fixed. `-ffp-contract=off` / `/fp:precise` were already set, so no FMA fusion can perturb it, and
x64/arm64 have no x87 excess precision.

Validated standalone against libm on BOTH platforms before wiring:

```
Sin  5.96e-08 (1 ULP)    ASin  1.19e-07
Cos  5.96e-08 (1 ULP)    ACos  2.38e-07
Tan  4.77e-07            Atan2 1.19e-07
```

`WWMath::Sin/Cos` and the `*Trig` wrappers all route to it, covering all 58 direct call sites.

Deliberately NOT done by quantising the transform before hashing: that hides the mismatch while the
peers go on simulating different worlds, turning a detected desync into an undetected one.

## What is still broken

Both peers now start **bit-identical** and drift apart during play. First differing frame observed at
255 in one run and 377 in another — it moves. This is an ordinary lockstep bug, not a cross-platform
maths problem.

Ruled out: libm (`[MATHCRC] 97B538BF` identical with 14 real calls executing), start positions (both
peers pick `posIdx=2` from identical RNG state), and load-time state (0 of 323 at frame 0).

Unexplained detail worth keeping: in one run frames 377 and 461 differed for exactly ONE frame each
and then **re-converged**, before splitting permanently at 541. A rounding difference does not heal
itself, so that may have a separate cause.

## Also fixed this session

* **Link-local addresses winning the LAN interface election.** POSIX enumeration filtered only on
  `IFF_UP`/`!IFF_LOOPBACK` and the list is ascending, so 169.254.x.x sorted ahead of 192.168.x.x and
  became the head that `LanLobbyMenuInit` takes. Ranks link-local last now.
* **iOS `z_wwaudio` never compiled on ANY Unix target.** `MilesStub.h` defined `HANDLE` as an
  object-like macro, so CompatLib's `typedef void *HANDLE;` expanded to `typedef void *void*;`. It
  went unnoticed because `build-macos-zh.sh` builds `--target z_generals`, which does not link that
  library. Long-standing, not a regression.
* **Release-visible diagnostics** for the whole LAN and CRC path — `[LAN] [CRC] [GXCRC] [GXOBJ]
  [GXMTX] [GXPOS]`. Without these the entire evening would have been invisible: in a shipping build
  a desync prints nothing and leaves one boolean byte in the .rep header.
* **Windows synthetic-input driver** (`drive-run-win64.ps1`) and its Mac counterpart
  (`drive-macos-zh.sh`), each documenting the failure modes found the hard way.

## Reverted, and why

`RTS_DEBUG_MULTI_INSTANCE` was enabled so this build could run alongside Generals Online — the
engine's named mutex is shared with retail Generals, so the second instance exits 1 silently. It
worked for that, but **it breaks LAN discovery**: `IPEnumeration.cpp:118-126` injects a loopback
address per instance, and 127.0.0.1 sorts below 192.168.x.x, so the peer advertises itself on
loopback. Reverted. To retry it, rank loopback last in `ipSortsBefore` first.
